## UI-20261029-01: explicit connection retry cannot recover a failed initial spectator join (P2)

Source: [public/app.mjs:77](../public/app.mjs#L77), particularly the unconditional `attemptedJoins.add(id)` before awaiting the join POST at line 78, and the visible Retry connection callback at line 206.

A spectator's first unauthenticated GET correctly returns 401, so the frontend begins its one automatic join. If that POST fails before delivery, the attempt marker remains in memory. The visible Retry connection button calls `openRoom()` again, but its new 401 is rejected because the marker is already set. The tab cannot recover through its displayed retry control; an entire page reload is required.

Reproduction in the committed driver:

1. Create a real human room using the normal UI and its real seat cookie.
2. Open its room link in a new browser context with no room cookie.
3. Abort only that context's first `/join` request with Chrome's `internetdisconnected` network failure, before it reaches the server. All other requests continue to the actual backend; no response is supplied or replaced.
4. Activate the visible Retry connection control by keyboard.
5. Observe one total join attempt, the feedback `Join this room to continue.`, and the still-visible Finding the beacon/Retry connection UI.
6. Reload as a positive control: a second real join succeeds and the returned seat is null (spectator).

Observed in all three runs. The final report records `afterVisibleRetry: {joinAttempts:1, stillFinding:true}` and `reloadControl: {joinAttempts:2, seatId:null}`. The driver fails the assertion that the visible retry should recover.

Impact: a transient initial join failure strands a new visitor until they discover the reload workaround. It does not grant a human seat or bypass auth. A correction should distinguish the bounded automatic join attempt from an explicit user retry, while retaining GET-before-join and preserving an existing human cookie. No correction was made in this initial pass.

## UI-20261029-02: elimination cancellation discards keyboard focus (P3)

Source: [public/panels.mjs:18](../public/panels.mjs#L18) and [public/app.mjs:197](../public/app.mjs#L197).

The elimination trigger has a focus key, and opening confirmation correctly focuses Confirm elimination. Its Cancel button has no focus key or explicit return target. Cancellation removes that focused button. `restoreFocus()` has no saved key to restore, so focus becomes BODY even though the original elimination trigger is available again.

Reproduction:

1. Use the real seeded human-saboteur room, with Pax alive and locally visible.

3. Focus Cancel and press Enter.
4. Read `document.activeElement`: actual `{tag:'BODY', key:null}`; expected the still-available `eliminate-p2` trigger.

Observed in all three runs. This is a keyboard navigation defect, not an elimination, auth or role-privacy bypass. It leaves the next Tab sequence at the document's navigation rather than at the action the user just canceled. A correction should explicitly restore focus to the trigger (or another documented logical target) after cancellation. No correction was made here; no screen-reader or formal accessibility conformance claim is made.

### Runtime changes

Only `public/app.mjs` and `public/panels.mjs` changed.

- Each `openRoom` captures a new local `opened` controller and uses that controller's signal for both the room GET and fallback join POST. Ownership requires matching room ID, epoch, global current controller and a non-aborted local signal. It is checked immediately in the unauthorized catch, before any fallback mutation, and again after completion. An obsolete deferred 401 therefore cannot issue a join or borrow the next room's signal.
- A join suppresses later automatic joins only after it acknowledges success while still owning the open. A failed join leaves the explicit Retry connection path usable. Every retry still GETs the room before considering a POST, so an uncertain success whose cookie arrived is recovered without an extra identity or changing an existing seat. A later 401 after an acknowledged join does not silently create a replacement spectator.
- Cancel elimination identifies its return target. The app first renders the latest state, then focuses only a connected, enabled trigger from the same room epoch. Disabled, removed and obsolete-epoch targets are not focused. Cancel also has a stable DOM focus key. No backend, shared, root configuration, other worktree, main or launcher change was made.
